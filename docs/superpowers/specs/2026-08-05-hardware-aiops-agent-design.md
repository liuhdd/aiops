# 硬件AIOps智能体设计文档

- 日期：2026-08-05
- 状态：已确认

## 1. 目标

构建一个面向算力中心的硬件AIOps多Agent协作智能运维系统：

1. **自主排查**：接收告警系统推送的告警数据，通过多阶段Agent流水线自主排查根因。
2. **对话排查**：用户通过Web聊天界面点名某条告警，Agent解释根因、给出处置建议。
3. 第一阶段所有外部系统数据（告警、监控指标、日志、CMDB、知识库）全部mock。

## 2. 技术栈与运行

- 后端：Go + Eino框架（LLM应用框架），LLM多供应商兼容（OpenAI兼容接口），API key从环境变量读取。
- 前端：React（Vite），包含告警列表、排查过程可视化、聊天界面三个视图。
- 持久化：SQLite（告警、流水线运行、阶段产物、聊天记录）。
- 部署：Docker Compose一键启动（后端 + 前端 + Nginx），mock数据持久化到SQLite。

## 3. 整体架构

```
┌─────────────────────────────────────────────┐
│                 React 前端                    │
│   告警列表视图 │ 排查过程可视化 │ 聊天界面        │
└───────────────┬──────────────┬──────────────┘
                │ REST/WebSocket
┌───────────────▼──────────────▼──────────────┐
│              Go 后端 (Eino)                    │
│                                              │
│  告警模拟器(定时推送) → 告警服务(入库)         │
│                                              │
│  流水线引擎:                                  │
│  接收规范化 → 过滤分诊 → 上下文收集           │
│   → 证据收集 → 根因分析 → 建议               │
│     (证据不足时有限回溯到证据收集,最多N次)     │
│                                              │
│  聊天Agent: 意图解析→点名告警→触发/追问流水线 │
│                                              │
│  mock数据源: 监控指标 | 日志 | CMDB | 知识库   │
│                                              │
│  持久化: SQLite(告警/流水线运行/阶段产物/聊天) │
└──────────────────────────────────────────────┘
```

- 每个流水线阶段是一个独立Agent/节点，输入输出为结构化中间产物，写入SQLite，前端实时订阅展示。
- 自动推送的新告警触发流水线；聊天里点名某告警可手动触发/追问。
- mock数据启动时生成并常驻内存，接口形式模拟真实系统。

## 4. 流水线阶段与中间产物

每个阶段是独立Agent（Eino节点），输入输出均为结构化中间产物（StageResult），持久化到SQLite：

| 阶段 | 输入 | 做什么 | 输出关键字段 |
|------|------|--------|-------------|
| 1. 接收规范化 | 原始告警 | 解析字段、归一化格式 | `Alert`(id, device, metric, severity, message, ts) |
| 2. 过滤分诊 | Alert | 去重(近期同类)、恢复判定、定优先级、决定是否继续 | `TriageResult`(deduped, priority, proceed) |
| 3. 上下文收集 | Alert | 查CMDB获取设备资产/位置/拓扑邻居；查历史告警 | `Context`(deviceInfo, neighbors, historyAlerts) |
| 4. 证据收集 | Alert+Context | 查监控时序(告警前后窗口)、查日志(相关关键字/时间窗) | `Evidence`(metrics, logs, gaps) |
| 5. 根因分析 | Context+Evidence | LLM综合证据→根因假设+证据链+置信度；若证据不足→回溯到4 | `RCA`(rootCause, evidenceChain, confidence, gaps) |
| 6. 建议 | RCA+Context | 匹配知识库预案，给出处置步骤 | `Recommendation`(actions, runbookRef, risk) |

回溯机制：阶段5若 `confidence < 阈值` 或 `gaps` 非空，带"补充查询指令"回到阶段4重跑（最多N=2次），每次重跑的证据追加保留在`Evidence`里形成迭代记录。

- 阶段2的 `proceed=false`（如已恢复/重复）时流水线提前终止并标记 `status=skipped`。
- 每个阶段产物记录 `stage_id, output, started_at, ended_at, iteration`，前端据此渲染时间线。

## 5. 聊天Agent与前端

**聊天Agent**（独立于流水线，用Eino ChatModel）：
- 意图解析：`列表查询` / `点名某告警` / `追问根因` / `问处置建议` / `查状态`。
- 点名告警时：若该告警流水线未跑过→触发；跑过→从SQLite读取结果回答，用户追问时带上下文多轮对话。
- 回复以结构化JSON+自然语言返回，前端渲染为聊天气泡，可嵌入流水线过程摘要。

**前端三个视图（React）**：
1. 告警列表：告警id、设备、指标、级别、时间、状态（排查中/完成/跳过）、置信度。
2. 排查过程可视化：单个告警的时间线，展示各阶段执行状态（待执行/进行中/完成/回溯）、每阶段产出的证据与结论、回溯的迭代次数。
3. 聊天界面：用户与Agent对话，支持点名"查一下alarm-10086是什么原因"。

**实时通信**：告警推送、流水线阶段进度通过WebSocket推给前端；查询类请求走REST。

**持久化表**（SQLite）：
- `alerts`：告警本身。
- `pipeline_runs`：每次流水线运行。
- `stage_results`：阶段产物（含iteration）。
- `messages`：聊天记录。

## 6. Mock数据、错误处理与测试

**Mock数据源**（启动时生成，常驻内存，模拟真实系统接口）：
- 监控指标：时序数据，围绕几台服务器/GPU节点生成CPU/内存/磁盘/GPU利用率/温度等指标曲线，含异常段（配合预置告警）。
- 日志：按设备生成syslog/应用日志，异常时段有报错关键字（OOM、磁盘IO error、NVLink down等）。
- CMDB：设备清单（名称/型号/机房/机柜/用途）+ 拓扑（依赖/邻居关系）。
- 知识库：故障处置预案（如"内存告警→查OOM日志→扩内存/调内核参数"）。
- 告警模拟器：定时推送预置的几种告警模板（CPU高、磁盘满、GPU掉卡、网络中断等），也可配置触发。

**错误处理**：
- 每个阶段独立try/catch，失败时该阶段标记 `status=failed` 并记录error，流水线标记 `degraded`，跳过该阶段产物继续后续（或终止，取决于阶段）。
- LLM调用失败→重试2次，仍失败则用阶段兜底（如根因分析输出"证据不足，需人工介入"）。
- WebSocket断线→前端重连+重拉状态。
- mock数据源查询超时/空结果→记为 `gaps`，驱动回溯。

**测试**：
- 单元测试：各阶段解析逻辑、分诊去重、回溯控制。
- mock数据源接口测试。
- 端到端测试：喂一条mock告警→跑完整流水线→断言各阶段产物与结论存在。
- 前端组件测试（Vitest）覆盖告警列表与时间线渲染。
